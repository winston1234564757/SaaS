## Before (поточний стан — з коду, не зі скріна)

**Що це насправді:** НЕ окремий route. Це `BookingDetailsModal.tsx` (708 рядків) у компоненті `Sheet` (`variant="adaptive"`): на мобілці — vaul bottom drawer (`max-h-96vh`), на десктопі — центрований dialog (`max-w-xl`, `max-h-90vh`). Відкривається через URL-параметр `?bookingId=` (M-BOOK-03 додав навігацію зі списків). Той самий архітектурний патерн, що `ClientDetailSheet` (M-CLI-06).

**Поточні секції (зверху вниз):**
1. `ClientIdentityHeader` (спільний M-CLI-06) — аватар-ініціал + ім'я + телефон + статус-піл, glow за кольором статусу.
2. **Дата/час картка** (`bg-secondary/40 rounded-3xl`) — дата + вікно часу; джерело (ручний/онлайн) + кнопка «Зателефонувати».
3. **Профіль клієнта** (LTV) — `ClientStatChips`: Візити / Виручка / Сер. чек (тільки якщо є `client_id`).
4. **Склад замовлення** — послуги (іконка+назва+тривалість+ціна) + товари + «Разом до сплати» + `PricingBadge`/Ambassador-бартер.
5. **Матеріали сеансу** — chips розхідників (тільки для `confirmed`).
6. **Нотатки** — коментар клієнта (`notes`, italic) + textarea нотаток майстра (auto-save 500ms debounce).
7. **Керування записом** (тільки `pending`/`confirmed`) — grid 2×: Підтвердити / Завершити / Перенести (розгортає `ReschedulePanel` зі smart-слотами) / Скасувати / «Клієнт не з'явився».

**Слабкі місця (моя оцінка):**
- **Візуальний різнобій контейнерів:** змішані `rounded-3xl` / `rounded-xl`, `bg-secondary/40` + `border` повторюється 5 разів — кожна секція виглядає як окрема плитка без єдиної ієрархії. Немає чіткого «героя».
- **Невикористані дані:** `status_changed_at` і `cancellation_reason` приходять у хуці, але **ніде не показані**. Для скасованого/завершеного запису це найважливіша інформація (коли, чому скасовано) — зараз її не видно взагалі. Прямий зв'язок із задачею M-DASH-07 (overlay скасувань хто/коли).
- **Дублювання uppercase-лейблів** `text-[10px] uppercase tracking-[0.2em]` ~8 разів — шум.
- **Завершений запис = глухий кут:** для `completed`/`cancelled`/`no_show` немає жодних дій і немає сумарі чому (для cancelled). Немає «Записати знову» / «До профілю клієнта».
- Хедер `ClientIdentityHeader` не клікабельний → у клієнта не перейти (хоча M-BOOK-03 уже завів патерн `clients?clientPhone=`).

## Дизайн-напрям (пропозиція до підтвердження)

**Тримаємо формат Sheet** (не промоутимо в окремий route): консистентність із `ClientDetailSheet`, нуль переробки навігації/back-handling, «сторінка» в беклозі = вільне формулювання. ← розгалуження Q1.

**Єдина вертикальна ієрархія замість 7 рівноважних плиток:**
- **Герой-блок** — клієнт + статус + дата/час як один зв'язний верх (не дві окремі картки). Хедер → клікабельний на профіль клієнта.
- **Receipt-логіка для складу** — склад замовлення оформити як «чек»: послуги/товари рядками, пунктирний роздільник, total акцентом. Це природний фіт для «деталі запису». ← розгалуження Q2 (receipt vs editorial).
- **Status timeline / причина** — новий блок: для `cancelled` → причина (`cancellation_reason`) + коли (`status_changed_at`); для `completed` → коли завершено. Закриває прогалину невикористаних даних.
- **Дії контекстні за статусом** — активні (pending/confirmed) як зараз; термінальні (completed/cancelled/no_show) → м'які вторинні дії «Записати знову» + «Профіль клієнта» замість глухого кута. ← розгалуження Q3.
- Уніфікувати контейнери (один радіус, один surface-патерн), прибрати дубль-лейбли.

**Обсяг файлів:** переважно `BookingDetailsModal.tsx`. Можливе перевикористання `statusGlow.ts`, `BOOKING_STATUS_CONFIG`, спільних `ClientIdentityHeader`/`ClientStatChips`. Бекенд/хук — НЕ чіпаю (усі потрібні поля вже приходять). Якщо «Записати знову» → переюз наявного BookingWizard-патерну з pre-fill (як M-BOOK-03 elements).

**Ризики:**
- `ReschedulePanel` (220 рядків smart-слотів) — НЕ переписувати логіку, лише візуально вписати. Регрес ризик якщо чіпати.
- Auto-save нотаток (хуки-порядок) — не зламати (урок M-CLI-03: усі хуки до conditional return).
- Десктоп dialog `max-w-xl` вузький для receipt у 2 колонки — receipt має лишатись 1-колонковим.
