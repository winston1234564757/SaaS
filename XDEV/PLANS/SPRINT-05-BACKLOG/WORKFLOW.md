## Ядро: Task Brief перед кодом

Перед будь-якою НЕтривіальною задачею (усе, крім типу COPY) я пишу `BRIEFS/[ID].md` — короткий розбір, який ти **підтверджуєш або виправляєш ДО написання коду**.

Сенс: якщо мій розбір кривий — ти ловиш це за 30 секунд читання, а не після 200 рядків не туди. Бриф — це твій реальний контроль якості, а не список питань навмання.

**Життєвий цикл задачі:**
```
1. mempalace_search по темі
2. Зібрати контекст: Read поточних файлів (+ СКРІНШОТ для redesign)
3. Написати BRIEFS/[ID].md  →  статус: DRAFT
4. Показати тобі → ти APPROVE або правки
5. SKILL declaration + Skill tool (спеціаліст з BACKLOG)
6. Код
7. Гейти за типом (див. нижче) → tsc → build
8. vercel --prod
9. TRACKER/HANDOFF/TRANSITION update → mempalace_add_drawer
10. BRIEFS/[ID].md → статус: DONE + root cause / рішення
```

## Рівні виконання (Tiers) — скільки процесу на задачу

Тип → тір. Тір визначає глибину і, головне, ПОСТ-чейндж гейт — звідки береться "чому так довго".

| Тір | Типи | Перед кодом | Скіли | Пост-гейт |
|-----|------|-------------|-------|-----------|
| **0 — Дрібний** | COPY · дрібний CSS/responsive (як `G-LAND-02`) | Інлайн міні-бриф (не файл), якщо немає реальної неоднозначності | Тільки якщо потрібне судження (`humanizer` для copy). Решта — внутрішні правила, БЕЗ важких скіл-доків | `tsc --noEmit`. Повний build — НЕ за задачу, а батчем |
| **1 — Стандарт** | REDESIGN · MOTION · BUGFIX · DATA | Task Brief (файл) + QA на реальних неоднозначностях | 1-2 спеціаліст-скіли | `tsc` + `build` |
| **2 — Важкий** | NEW-FEATURE · великий редизайн (`M-ANL-01`) · `M-GROW-02` | brainstorming + spec-driven + повний brief (acceptance, стани) | spec → impl → adversarial-reviewer | `tsc` + `build` + `ship-gate` (+ тести) |

### Правила ефективності (виведені з прогону G-LAND-02)
1. **Повний build НЕ за кожну дрібну задачу.** Тір 0 → `tsc` достатньо; повний build один раз батчем перед деплоєм. Прямий фікс "чому так довго".
2. **Батч QA в ОДИН `AskUserQuestion`** (2-4 питання). Ніколи серійні раунди.
3. **Відповіді на QA = підтвердження брифа.** Не питати окремо "апрувиш бриф?".
4. **Скіл має context-ціну.** Кожен `Skill()` вантажить великий док у контекст. На Тірі 0 не вантаж важкі дизайн-скіли заради 3 класів — застосовуй внутрішні правила (CLAUDE.md, Frost-токени). Скіл — лише коли потрібне судження, якого нема в пам'яті.
5. **Не вигадуй неоднозначність.** QA — тільки на реальні розгалуження. Нема їх → бриф→код без питань.
6. **Скріншот для REDESIGN — self-serve за замовчуванням:** я сам запускаю dev і знімаю екран. Ти даєш свій лише якщо мій не показує проблему. Прибирає скріншот як блокер.

> Ретроспектива G-LAND-02: за цими правилами це Тір 0 — мав бути `tsc` без повного build і без завантаження `design-taste-frontend` (3 класи = внутрішні правила). Тоді задача була б помітно швидшою. Повний набір ганяли свідомо, для валідації машинерії.

## Найдорожчий вхід: скріншоти

Для **REDESIGN** і **MOTION** скріншот поточного стану — не опція, а вимога. Без візуального якоря "преміальний редизайн" = я вгадую. Якщо скріна немає — або даєш його, або я спершу запускаю `run` і дивлюсь сам, ДО брифа.

> ⚠ Папку `Screens/` видалили з git. Треба домовитись, де лежать скріни поточних екранів, або я генерую їх через dev-сервер перед кожною redesign-задачею.

## Антипатерн (чого НЕ робимо)

- Однаковий важкий spec на тривіальну COPY-задачу — церемонія заради церемонії.
- Redesign без скріншота — вгадування.
- Bugfix із дизайн-питаннями замість root cause — лікування симптому.
- "[MANDATORY] напиши код" від keyword-хука на задачу, де код ще не на часі — ігнорувати, орієнтуватись на тип з цього файлу.
- Повний `npm run build` після кожної дрібної зміни — непропорційно (1-3 хв заради 3 класів). Тір 0 = `tsc` + батч-build.
- Завантаження важкого скіл-доку заради тривіальної зміни — зайва context-ціна.
- Серійні раунди `AskUserQuestion` — батчити в один виклик.
