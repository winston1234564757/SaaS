# R2 Backend/API Audit — 08-backend-api

Date: 2026-07-07 · Launch: 2026-07-10 (public domain + real Monobank)
Scope: API routes (`src/app/api/**`), server actions (`actions.ts`), cron routes, Nova Poshta integration, external-API failure isolation (Telegram / TurboSMS / Push / Resend / NP), N+1 / pagination / waterfalls. Priority on surfaces new since 2026-06-20 (shop + NP, `/my/*` cabinet, dynamic pricing, broadcasts, C-DESK-01).
Mode: READ-ONLY. No project files edited.
Non-duplication: findings already covered by 01-security (IDOR RPC cluster, telegram `/start <uuid>` rebind, NP quota, createOrder DoS), 07-database, 09-auth (OTP/PostBookingAuth/register), 10-billing (mono-webhook, recurring engine, createOrder oversell/COD) are NOT repeated here except where a distinct code path is involved.

## Headline
One genuine **P0 account-takeover** exists that no prior audit covered: `/api/auth/telegram/link-phone` trusts a **client-supplied phone number** and hands back a login token (magiclink OTP) for the account owning that phone — anyone with a valid Telegram `initData` (i.e. anyone who opens the bot) can log in as any phone-registered user, including masters. That is the launch blocker. Beyond it, the backend is mostly disciplined: server actions consistently re-derive identity from `auth.getUser()` and scope writes by `master_id = user.id`, booking prices are server-recomputed, and external-API calls are failure-isolated so a dead Telegram/SMS/Push provider cannot break a booking. The remaining real risks are a **client_id spoof** on anonymous bookings (forge ownership + drain a victim's referral-bonus balance), **reminder/briefing crons that effectively never fire** because their Vercel schedule (daily) contradicts their hourly-window design, and **input-validation gaps in the shop order path** (negative/zero quantities accepted, non-atomic stock decrement, no rate limit) that corrupt the stock ledger and totals.

## P0 — Critical (BLOCK LAUNCH)

`[P0] src/app/api/auth/telegram/link-phone/route.ts:9-82 — account takeover via unverified client-supplied phone.` The route validates `initData` (HMAC — proves only that the caller controls *some* Telegram account, `tgUser.id`), then reads `phone` **directly from the request body** and calls `ensureTelegramClientIdentity({ phone, telegramChatId })`. That helper (`src/lib/telegram/ensureTelegramClientIdentity.ts:27-59`) looks up the existing profile **by phone**, rebinds its `telegram_chat_id` to the caller, then the route calls `admin.auth.admin.generateLink({ type:'magiclink', email: virtualEmail(phone) })` and returns `token: linkData.properties.email_otp` in the JSON response (line 79). Failure: attacker opens the bot Mini-App, copies their own valid `initData`, and `POST`s `{ initData, phone: "<victim phone>" }` via curl → server returns a magiclink OTP for the victim's virtual email → attacker verifies it and is logged in **as the victim**. All phone-registered accounts (SMS-OTP is the primary auth path, so the majority — including masters with full CRM/billing access) are takeover-able knowing only the phone number. Contrast the *safe* sibling `src/app/api/auth/telegram/route.ts:51-81`, which looks the profile up **by verified `telegram_chat_id`** and never trusts a supplied phone. No frontend calls `link-phone` (grep: zero callers) — it is orphaned but **still deployed and live**. Not covered by 09-auth (that scope was OTP/PostBookingAuth/register). Fix: delete the route, or require the phone to come from a Telegram-verified contact (as the `/api/auth/telegram` + contact-webhook flow already does) and never return a login token for an account the caller has not proven ownership of.

## P1 — High

`[P1] src/lib/actions/createBooking.ts:102 + 118-136 + 519 — client_id is spoofable on anonymous/online bookings.` `resolvedClientId` is initialised from the **client-supplied** `p.clientId` (line 102). For `source==='online'` the override to `user.id` only happens inside `if (user)` **and** only when the caller's role is `client` (lines 121-133). So for an **anonymous** online booking (no session — the common public-page path) the `if (user)` block is skipped entirely and `resolvedClientId` stays equal to the attacker-supplied `p.clientId`; likewise an authenticated master/unknown role falls through with `resolvedClientId = p.clientId` (the code comment on line 134 claims "masters / unknown → null", which is **false**). `p.clientId` is only shape-validated (`z.string().uuid()`). Failure: an anonymous attacker who knows a victim's `client_profiles.id` (UUID) books with `clientId=<victim>` → the booking is inserted with `client_id=<victim>` (line 519), polluting the victim's `/my/bookings` history, and — worse — the C2C referrer-bonus path (lines 432-442, 664-674) reads `get_c2c_balance(resolvedClientId=victim)` and inserts `c2c_bonus_uses(referrer_id=victim, discount_used=…)`, **spending the victim's accrued referral-bonus balance** to discount the attacker's own booking. Precondition: a valid victim UUID. Fix: for online bookings derive `client_id` solely from the authenticated session (never from the payload); drop `p.clientId` from the online branch.

`[P1] vercel.json:8-9,5-6 vs src/app/api/cron/reminders/route.ts:7-19,47 & src/app/api/cron/check-uncompleted/route.ts:11 — reminder crons scheduled daily but coded for hourly cadence; morning briefings never fire.` `reminders/route.ts` is documented "Vercel Cron: щогодини" and matches bookings against three tight windows (24h/2h/30m ahead, ±29/±14 min tolerance), and only sends the 08:00-Kyiv master briefing when `kyivHour() === 8` (line 47). But `vercel.json` schedules it at `"0 7 * * *"` — **once per day at 07:00 UTC**. 07:00 UTC = 09:00/10:00 Kyiv, so `kyivHour()` is never 8 → **morning briefings never send at all**, and the 2h/30m/24h windows only coincidentally match the handful of bookings whose start time lands inside a ±29-min window of the single daily run → the vast majority of appointment reminders (a core product feature, and the only SMS-critical delivery path) **silently never fire**. `check-uncompleted` has the same daily-vs-hourly mismatch (`"0 17 * * *"` vs code comment "щогодини `0 * * * *`" + a 55-min idempotency window designed for hourly runs) — MEMORY confirms this one is knowingly "pending Vercel Pro". Failure: clients miss reminders, masters miss the 2h heads-up and the daily briefing. Fix: move both crons to hourly (`0 * * * *`) once on Pro, or rewrite the windows to a daily cadence; verify the briefing hour against the actual UTC run time.

## P2 — Medium

`[P2] src/app/(master)/dashboard/products/actions.ts:349-355 + src/app/[slug]/actions.ts:147-153 — order quantity is never validated (negative / zero / fractional accepted).` `createOrder` / `createPublicOrder` take `qty` as an unvalidated `number` (no Zod, unlike `createBooking` which enforces `.positive().int()`). With `qty = -5`: the stock check `p.stock_qty < item.qty` (`10 < -5`) passes, `total_kopecks += price * -5` goes **negative**, and the decrement `update({stock_qty: p.stock_qty - qty}).gte('stock_qty', qty)` computes `10 - (-5) = 15` with a `.gte(-5)` guard that is always true → **stock is inflated** and a negative-total order row is written. Failure: public attacker creates free/negative orders and corrupts both `products.stock_qty` and the `product_transactions` ledger. Fix: validate `qty` as a positive integer (Zod) in both public order actions.

`[P2] src/app/[slug]/actions.ts:118-216 (createPublicOrder) — public, unauthenticated, non-atomic stock decrement, no rate limit.` Distinct from the `createOrder` path already flagged in 01-security/10-billing. Same TOCTOU: reads `stock_qty` (line 150), writes `update({stock_qty: p.stock_qty - qty}).gte('stock_qty', qty)` (lines 201-205) **without checking the affected-row count**, so two concurrent last-unit orders both create an order + both insert a `sale` `product_transactions` row while only one update lands → oversell + ledger drift. It also does **not** use the atomic `decrement_product_stock_atomic` RPC that the hardened `createBooking` path uses (createBooking.ts:602) — the order paths were left on the unsafe pattern. No rate limit → inventory-drain / order-spam DoS. Fix: route both order actions through the atomic decrement RPC and add a per-phone/IP throttle.

`[P2] src/app/(master)/dashboard/marketing/actions.ts:293-363 — sendBroadcast processes recipients in a serial awaited loop with no batching / no after(); large lists time out and strand the broadcast.` Each iteration awaits: `broadcast_recipients` insert → `broadcast_links` insert → conditional `phone_discounts` insert → `notifyClientBroadcast` (push + Telegram + SMS, each a network round-trip) → `broadcast_recipients` update — all sequentially. For a master with 100+ clients this comfortably exceeds the Vercel function timeout. Failure on timeout: the loop dies mid-way, the broadcast is left in `status:'sending'` **forever** (only set back to `'sent'` at line 357 after the loop), `broadcasts_used` is never incremented (so the Starter limit isn't consumed), and `phone_discounts` are half-created → inconsistent state with no recovery path. Fix: batch with `Promise.allSettled`, cap per-invocation and continue via a queue, or run under `after()` with chunked commits and a resumable status.

`[P2] src/app/api/push/subscribe/route.ts:44-47 — push subscription upsert keyed on endpoint is not scoped to the caller.` `upsert({ user_id: user.id, endpoint, subscription }, { onConflict: 'endpoint' })` lets an authenticated user re-bind an existing `endpoint` row to **their own** `user_id`. Push endpoints are high-entropy/secret so exploitation is unlikely, but a leaked endpoint could be stolen (attacker starts receiving the victim's notifications) or, more plausibly, a shared-device endpoint silently migrates between accounts. Low likelihood, real authorization gap. Fix: on conflict, only overwrite when the existing row's `user_id` matches, or delete-then-insert scoped by `user_id`.

## P3 — Low / hardening

`[P3] src/lib/telegram.ts:27 + src/lib/novaposhta/client.ts:31 + src/lib/push.ts:31 — no fetch timeout on Telegram / Nova Poshta / web-push calls (only TurboSMS has one).` `sendTurboSMS` uses an 8s `AbortController` (turbosms.ts:7-8, 21) — good. `sendTelegramMessage`, the NP `npCall`, and `webpush.sendNotification` have **no** timeout. Failure: a slow/hung Telegram API stalls any handler that awaits it — e.g. `cancelBooking` awaits `sendTelegramMessage` at my/bookings/actions.ts:121 *after* the DB cancel, so a Telegram stall delays the user's response up to the platform limit. Booking correctness is unaffected (notify runs post-commit and is `.catch`'d elsewhere), so this is availability-only. Fix: wrap all three in an `AbortController`/`Promise.race` timeout like TurboSMS.

`[P3] src/app/(master)/dashboard/products/actions.ts:417-421 — N+1 inside createOrder's per-item loop.` For every order item the loop issues a separate `products.select('name, stock_alert_threshold').eq('id',…).single()` even though the product `name` is already in `productMap` and only `stock_alert_threshold` is missing. N extra round-trips per order. Fix: add `stock_alert_threshold` to the initial `.in()` fetch at line 339 and drop the per-item query.

`[P3] src/app/(master)/dashboard/clients/actions.ts:33-96 (sendChurnReminder) — no ownership check on clientId, no rate limit.` The action sends push + Telegram to the supplied `clientId` without verifying that client belongs to the calling master. A master (or a compromised master session) can push a self-branded "book with me" message to arbitrary user UUIDs. Low impact (own-branded, needs valid UUIDs) but it is unauthorised outbound messaging. Fix: verify `client_master_relations(master_id=user.id, client_id)` exists before sending; throttle.

`[P3] src/app/(master)/dashboard/products/actions.ts:330-332 + createPublicOrder — Nova Poshta destination refs are not validated against the NP API.` `createOrder` requires `np_warehouse_ref` to be present for `delivery_type==='nova_poshta'` but never verifies `np_city_ref`/`np_warehouse_ref` are real NP references. Failure: a client (or a tampered payload) submits garbage refs → order saved with an unshippable address; the master discovers it only at fulfilment. Data-quality, not security. Fix: server-side validate the ref pair via the existing NP client before insert.

`[P3] src/app/my/bookings/actions.ts:189-200 (submitReview) — no guard against duplicate reviews per booking/order.` The insert into `reviews` has no visible "already reviewed" check; unless a DB unique constraint on `(booking_id)` / `(order_id)` exists (not confirmed from the migration set read here), a client can submit unlimited reviews for the same completed booking → review-feed and master-notification spam. Fix: enforce a unique constraint on `reviews(booking_id)` / `reviews(order_id)` and pre-check.

`[P3] src/app/api/marketing/send-story/route.ts:8-56 — no size cap on the base64 dataUrl before Buffer allocation.` Authenticated masters only, but an oversized `dataUrl` is decoded straight into a `Buffer` (line 56) with no length limit → memory-pressure vector on the function. Low. Fix: reject payloads above a sane image size before decoding.

`[P3] src/app/(master)/dashboard/studio/actions.ts:71-74 (joinStudio) — sets subscription_tier='studio' with no billing hook.` Joining via invite token grants the paid Studio tier directly. This is the intended studio model (owner billed per master) but there is no server-side link to a per-master charge — ties into 10-billing's flat-STUDIO_KOPECKS / `wip` note. Token is single-use with rotation (correct). Flagged for cross-reference, not exploitable alone.

## Verified safe ([OK] / [INFO])

- `[OK] src/lib/novaposhta/client.ts:1,24 — NP API key is server-only.` `import 'server-only'`, key read from `process.env.NOVAPOSHTA_API_KEY` inside the server module and never serialised to the client. Response validation checks `res.ok` and `json.success`, returning `[]` on failure (no throw leaking to the caller). Public lookup actions (`novaPoshta.ts`) expose only city/warehouse name+ref.
- `[OK] External-API failure isolation.` `sendTelegramMessage` (try/catch → `false`), `sendTurboSMS` (try/catch + 8s abort → `{ok:false}`), `sendPush` (try/catch → `{ok:false,gone}`) all swallow errors; `NotificationOrchestrator` runs channels under `Promise.allSettled` and `.catch`; `createBooking` awaits notify **after** the booking is committed and wraps it in `.catch` (createBooking.ts:684-694). A dead Telegram/SMS/Push/Resend provider cannot fail a booking or an order. NP failures degrade to an empty picker, not an error.
- `[OK] Cron auth is first-line in all five routes.` `verifyCronSecret` (HMAC-normalised `timingSafeEqual`, verifyCronSecret.ts:3-12) is the first statement in reminders / rebooking / check-uncompleted / expire-subscriptions / reset-monthly, returning 401 before any DB access.
- `[OK] Cron idempotency.` check-uncompleted uses a 55-min `notifications` de-dup window; rebooking relies on `get_rebooking_due_clients` RPC dedup; NotificationOrchestrator logs to `notification_logs`. (Cadence is the problem, not idempotency — see P1.)
- `[OK] Telegram Mini-App auth (the used path).` `src/app/api/auth/telegram/route.ts` and `intent/route.ts` validate `initData` HMAC (24h expiry) and key off the **verified** `telegram_chat_id`, never a supplied phone. `set-role-intent` sets an httpOnly cookie with Zod-validated role. These are safe — the P0 is confined to the orphaned `link-phone` route.
- `[OK] Server-action authorization pattern.` Products, clients, pricing, marketing, studio, my/bookings, my/profile actions all re-derive identity via `auth.getUser()` and scope every write with `.eq('master_id', user.id)` / `.eq('client_id', user.id)`; `createAdminClient()` is used only after that self-scoping. `updateBroadcast`/`deleteBroadcast` additionally gate on `status='draft'`. No action was found using the admin client to write cross-tenant data on unvalidated input (other than the createBooking/createOrder input gaps above).
- `[OK] Booking price integrity (re-confirmed).` `createBooking` re-fetches canonical service/product prices from the DB, ignores client price hints, caps discounts at 40%, clamps totals `Math.max(0,…)`, and enforces the Starter 40/month limit and manual-source master-role check server-side.
- `[INFO] telegram/webhook `/start <uuid>` rebind` and `createOrder` DoS/oversell are already documented in 01-security / 10-billing; not re-scored here.
