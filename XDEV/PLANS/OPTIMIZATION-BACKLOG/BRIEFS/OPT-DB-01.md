# OPT-DB-01 — useOrders full-scan orders + УСІХ bookings без обмеження

**Тип:** DATA
**Пріоритет:** P0
**Статус:** DRAFT
**Спеціаліст-скіли:** `sql-query-optimization` `database-optimizer`

---

## Поточний стан
`src/lib/supabase/hooks/useOrders.ts:68-120` (хук `unified-sales`, вкладка продажів).

Два запити, обидва scoped ЛИШЕ по `master_id`:
- `:68-79` — `orders` + `order_items` + `products`, без date-фільтра, без `.limit()`.
- `:111-120` — `bookings` + `booking_products!inner`, теж без date/limit; тягне **кожен** booking, що колись мав товар.
- `statusFilter` для bookings застосовується у JS (`:139`), не в запиті.

На кожен рендер вкладки перекачується вся історія замовлень + усі booking'и з товарами, десеріалізується в JS. Найгірший full-scan клієнтського шару. Зростає необмежено.

## Ціль
Обмежити обидва запити: date-window (напр. останні N місяців) + `.limit()` з пагінацією; статус-фільтр перенести в запит (`.eq('status', ...)`) для bookings так само, як уже зроблено для shop (`:81`).

## Файли, які чіпаю
- `src/lib/supabase/hooks/useOrders.ts` — обидва запити + ключ `useQuery` (додати межу до `queryKey`, `:60`).
- Споживач вкладки продажів (перевірити, чи потрібен UI «показати ще»).

## [DATA] Схема пайплайну
`orders`/`bookings` (RLS scoped master) → merge у `UnifiedSale[]` → сортування за `created_at` → рендер. Рветься на етапі fetch: немає верхньої межі рядків. RLS уже обмежує майстром — семантика не зміниться від додавання date/limit, лише обсяг.

## Ризики / що може зламатись
- Пагінація змінить UX вкладки — узгодити «завантажити ще» vs date-window за замовчуванням.
- `booking_products.product_price` в UAH → kopecks множенням (`:132`) — не чіпати логіку конвертації.
- Статус-фільтр bookings у JS (`:139`) прибрати обережно — `mapBookingStatus` мапить booking-статуси на order-статуси; фільтр по сирому `status` у запиті ≠ по mapped. Можливо, фільтр лишити в JS, а обмежити тільки date+limit.
