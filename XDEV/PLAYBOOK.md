## I. Дизайн-закони (founder)

Народжені з реальних founder-корекцій. Кожен — про **мислення**, не про піксель.

### 1. Закон темного блоку
Кожна поверхня = один **темний блок-герой** (editorial-обкладинка, одна домінанта, драма) + **світлі блоки-тіло** (служать, hairline, тихо). Проектуй **з концепту з нуля** (метафора: «досьє», «чек», «P&L», «ритм бізнесу») — **НЕ ретрофіть** легасі-віджет косметикою. Маркер провалу = **рівномірність** (N однакових карток/барів = дитсадок). *Народжено на M-ANL-01: founder схвалив темний editorial-блок, відкинув світлі картки. Повний канон — DESIGN_LANGUAGE §Закон темного блоку.*

### 2. Крафт світлих блоків
«Служить» ≠ «нудний». Founder: «більше крафту над світлими блоками». Кожен `Section`: featured-диференціація (свіжий елемент багатший) + домінантна типографіка (`metric-value`/`heading-serif`) + hairline-структура. Драма можлива й на світлому — типографікою та ієрархією, не лише темрявою. Нуль N-однакових рядків.

### 3. Повні сторінки, не hero
DS-задача на поверхню = аудит+редизайн **КОЖНОГО блоку** сторінки (включно суб-компоненти), не звуження до hero-секції. Власні очі = жива **повна** сторінка, не ізольований шматок.

### 4. No-Emoji аватарів → монограм
Аватар майстра без фото → **НІКОЛИ** emoji-fallback. Завжди **designed монограм-обкладинка**: детермінований Frost-hue (`linear-gradient`) + Cormorant-ініціал. Реюз `monogramHue`/`initialOf`/`CORMORANT` з `explore/shared.ts` через спільний `MasterAvatar`/`MediaCover`. Founder: «прибирай емодзі всюди». BookIT — преміум, не дешевий booking-app.

### 5. Калібрований контраст на Frost
Токени `--success`/`--warning` відтюнено під великий розмір і **провалюють 4.5:1 на дрібному** (12px ≈ 3.95 на periwinkle-картці). Для тексту-статусу: good `#0B6B2E` · warn `#9A4508` · bad `--error #B91C1C`. **`--text-tertiary`/`text-muted-foreground` (2.78:1) = забанене — НІКОЛИ для тексту**; ієрархію нести розміром, не третім тоном. On-dark: `white/55` мінімум для дрібного (6.0), статуси — світлі тінти (emerald/amber/rose-200). Завжди перевіряй пари.

## II. Процес (founder + agent)

### 1. Task Brief перед кодом — реальний контроль якості
Перед нетривіальною задачею: `mempalace_search` → Read живого коду (+скрін для redesign) → `BRIEFS/[ID].md` (Before + напрям + файли + ризики) → **founder APPROVE** → код. Сенс: кривий розбір ловиться за 30с читання, а не після 200 рядків не туди. «Довіряю» ≠ «роби без узгодження».

### 2. Глибина процесу масштабується за типом
Не однаковий важкий процес на все. **Тір 0** (COPY, дрібний CSS) → `tsc`, без важких скілів, build батчем. **Тір 1** (REDESIGN/BUGFIX/DATA) → Brief + 1-2 скіли + `tsc`+build. **Тір 2** (NEW-FEATURE, великий редизайн) → spec + adversarial-review + ship-gate. Церемонія по розміру задачі — не менше й не більше.

### 3. NO OVERTHINKING — вибрав підхід → одразу код
Не палити токени на роздуми. QA-питання батчити в **один** `AskUserQuestion` (2-4), ніколи серійно. Питати тільки на **реальні** розгалуження — вигадана неоднозначність = марнування. Відповіді на QA = підтвердження брифа (не питати окремо «апрувиш?»).

### 4. Власні очі ДО показу founder (закон #4 редизайну)
Прев'ю-роут (мок-дані + реальні компоненти, поза auth) → Playwright headless → дивлюсь сам → самокритика проти законів → показ founder **лише сильного варіанту**. Сліпий deploy-і-чекання-скріна = спалені цикли + фрустрація. Прев'ю видаляти перед commit.

### 5. Автоматичні гейти (без нагадувань)
Кожна зміна: `tsc:0`. Кожен новий UI-рядок → **humanizer** (прибирає em-dash, AI-tells). Кожен Cyrillic-файл перед Edit → **encoding-чек** (cp1251-mojibake, curly quotes). Після коміту коду → **Sprint Pipeline** (TRACKER→HANDOFF→TRANSITION→git→mempalace→SYSTEM_MAP). Важливе рішення → `mempalace_add_drawer`.

## III. Інженерні патерни (agent — дистильовані з усього беклогу)

Технічні рішення, що повторно себе виправдали. Це «як робити правильно», а не «що зробили».

### 1. Own-eyes через прев'ю-роут — навіть для живого зовнішнього API
Ізольований `ds-preview` роут з мок-даними → Playwright скрін кожного стану. Працює і для складних поверхонь (мокай важкі провайдери), і для **живих server actions** (реальний виклик — так верифікували живий Nova Poshta API: Львів→міста→відділення→payload). Урок: `next/image` кидає на не-whitelisted host ДО onError → прев'ю роби з `avatarUrl:null`.

### 2. Стан рідких даних — ОБОВ'ЯЗКОВИЙ
Founder-акаунт має мало записів → графіки/сітки **вироджуються**, редизайн невидимий. Кожен data-віджет: `0`→empty · рідко→editorial-текст/список · густо→повна візуалізація. ЗАВЖДИ рендерити прев'ю на рідких даних, не лише густий seed. Часто «дані» насправді означають «порожньо» (5 однакових пілів = «все вільно»).

### 3. Shared-примітив → opt-in проп, НЕ переписуй
Перед редизайном спільного компонента (chat, картки) — grep, чи не юзає його майстер/інша зона. Якщо так → додай **opt-in проп default-off** (`contained`/`inPane`), не форкай і не переписуй. Майстер/мобільний лишаються **byte-identical**. *(ChatShell contained-режим для десктоп-2-pane.)*

### 4. Route-aware ширина контейнера
Sidebar-офсет (`pl-264px`) сам по собі **НЕ достатній** — внутрішній `max-w-lg` затискає master-detail у 512px. Новий wide-десктоп-роут ОБОВ'ЯЗКОВО додати в `isWideDesktopRoute` (layout). Латентний баг легко проґавити, якщо own-eyes робити в ізольованому прев'ю без реального layout.

### 5. Desktop-стратегія за складністю структури
Окреме `hidden lg:block` дерево — ЛИШЕ коли структура кардинально інша (master-detail, 2-pane, featured-галерея, 2-кол читацька). Прості форми/списки → **responsive-класи на тому ж дереві** (менше дублювання, спільний стейт). Не будуй друге дерево там, де досить `lg:grid-cols-*` + `lg:max-w-*`.

### 6. Side-effect хука → гейтуй його
`useChatViewport` лочить `document.body.overflow` поки змонтований — на десктопі в pane це вбило б скрол сторінки. Хук із side-effect мусить мати `enabled`-параметр, щоб contained-режим його вимикав. Завжди перевіряй, що робить хук ПОЗА рендером.

### 7. Плаваючі елементи vs sidebar
Fixed-елементи (cart-піл, save-FAB) на десктопі не мають лізти під 264px sidebar. Якщо тільки authed `/my` → статик `lg:left-[264px]`. Якщо guest+client поверхня (shop) → CSS `body.has-client-shell .element{left:264px}` (guest недоторканий).

### 8. Supabase міграції через Management API (обходить friction `db push`)
`POST https://api.supabase.com/v1/projects/{ref}/database/query` з `Authorization: Bearer <PAT>` + `{"query":"..."}` виконує **будь-який SQL** на прод-БД без інтерактивного `supabase link`/DB-паролю. DDL повертає `[]`. Верифікуй через `information_schema.columns`. PAT у `.env.local` (git-ignored). *(CLI залінковано: ref `sqlrxsopllgztvgrerqk`.)*

### 9. Turbopack dev-cache recovery
Dev періодично панікує (500 + `TurbopackInternalError` SST) після `rm .next` під час активного dev або кількох інстансів. Фікс: **kill усі node** (PowerShell `Stop-Process`) + `rm -rf .next` + **ОДИН** чистий `npm run dev`. Після видалення прев'ю-роуту build падає на стале `.next/dev/types` → теж `rm -rf .next`.

### 10. Windows git-bash: Cyrillic у curl ламається
`curl -d` з Cyrillic у git-bash кодує в cp1251 → зовнішнє API відповідає «Data is invalid» (не помилка ключа!). Передавай JSON через `python -c json.dumps` або `--data-binary @file` (UTF-8). У Node `fetch`+`JSON.stringify` — UTF-8 коректний. Не сплутай артефакт кодування з битим ключем/API.

### 11. Деплой: env → prod → smoke
`vercel env add NAME production` (значення через stdin) → `vercel --prod --yes` → smoke-тест (`curl` кількох роутів = 200). Секрети з `.env.local` (локальні) ОКРЕМО додаються у Vercel env — інакше прод не бачить ключа. `.env.local` не переживає reset сесії — `grep -c KEY .env.local` перед own-eyes; dev читає env лише на старті.

### 12. Git-гігієна: категоризуй, gitignore шум, логічні коміти
Перед «зроби красіво» — **проаналізуй природу** брудного стану (не `git add -A` наосліп). Авто-генерований стан (session/compact json, `.claude-flow` stores, `__pycache__`, `lint_output`) → `.gitignore` + `git rm --cached` (щоб не висів щосесії), НЕ комітити. Осмислене (path-fixи, docs) → окремим логічним комітом. Розділяй шум від змісту.

## IV. Загальні патерни роботи та логіка дій

> Не BookIT-специфіка — про те, ЯК думати й діяти, щоб робота була швидкою, правильною і без переробок. Операційна система під усіма законами вище. Кожен патерн — з реальним якорем із беклогу.

### Розуміння перед дією
1. **Живий код — істина; план/док — гіпотеза.** Перед рішенням читай реальний код, не пам'ять і не опис у беклозі. *REAUDIT казав «Analytics найгірший §4» — live-grep: уже конформний; нотатка «87 темних occ» — live-grep: 5 світлих. Anti-sycophancy live-grep економить години не туди.*
2. **Grep консумерів перед зміною спільного.** Хто ще юзає цей компонент? *Так з'ясувалось, що ChatShell юзає й майстер → opt-in проп замість переписування.*
3. **Трасуй потік даних end-to-end.** Перед зміною revenue-flow — джерело → трансформ → запис → відображення. Інакше зламаєш те, чого не бачив. *(checkout → createOrder → orders + stock.)*
4. **Категоризуй перед масовою дією.** *65 брудних файлів — спершу аналіз природи (1 інший вміст, решта path-fix), тоді розділені коміти. НЕ `git add -A` наосліп.*

### Рішення: коли питати, коли вирішувати сам
5. **Питай лише те, що РЕАЛЬНО змінює що будувати.** Обсяг revenue-critical, зовнішній блокер, розгалуження без очевидного дефолту → `AskUserQuestion`. Решта → розумний дефолт + згадай його + продовжуй. Вигадана неоднозначність = спалені цикли founder.
6. **Рекомендуй, не влаштовуй опитування.** Перший варіант = «Recommended» з причиною. Нейтральний список перекладає твою роботу на founder.
7. **Батч питань в один виклик** (2-4), ніколи серійно.
8. **Делегування ≠ вседозволеність.** «Все закінчуй автономно» → веди сам, але зупиняйся на рішеннях зі справжньою ціною (обсяг, гроші, незворотність). «Обирай найкраще» ≠ «будуй ТТН на вгаданих даних».

### Верифікація: доказ, не припущення
9. **Тестуй саму річ, не проксі.** `tsc:0` ≠ «працює». Ганяй реальний потік: живий NP API (не мок), рендер власними очима, smoke після деплою.
10. **Підтверджуй, що фікс узявся.** *Міграція застосована → query `information_schema` → побачив 4 колонки.* Не «команда відпрацювала» — «результат на місці».
11. **Відрізняй артефакт від справжнього провалу.** *curl «Data is invalid» = Windows-кодування, не битий ключ. Фейк-ключ дав ту саму помилку → справа не в ключі.* Ізолюй причину перед лікуванням.

### Чесність у дії (anti-sycophancy)
12. **Підсвічуй знайдене побіжно.** *Латентний squeeze bookings у `max-w-lg` — назвав і полагодив, не сховав.*
13. **Називай борги прямо**, до того як founder спіткнеться. *«Міграцію не застосую через CLI», «ТТН потребує даних, яких нема».*
14. **Не переоцінюй зроблене.** *«Own-eyes в ізольованому прев'ю, НЕ в реальному authed — раджу твоє QA».* Точний статус > оптимістичний.
15. **Флагуй відхилення від плану** — що і чому. *(Пересеквенсив DS-MODAL, бо booking flow revenue-critical.)*

### Скоуп і межі: не over-reach
16. **Мінімальний blast radius.** Opt-in проп default-off · additive nullable-міграція · mobile byte-identical. Зміна не тече за свою межу.
17. **Не роби найризикованіше наосліп.** Не переписуй shared-примітив, не будуй ТТН на припущеннях, не `git add -A`. Безпечну цінну частину — зараз; ризиковану/заблоковану — окремо з нотаткою.
18. **Поважай межу задачі.** *«Мобільний недоторканий» = навіть emoji-fallback лишаємо, поки не окрема директива.* Не роздувай скоуп «заодно».

### Незворотність і секрети
19. **Confirm-first для outward-facing/незворотного.** Деплой на прод — лише з явною авторизацією founder + smoke-тест після.
20. **Секрети — у правильне місце.** Ключ → `.env.local` (git-ignored, перевірив `git check-ignore`), не в чат/трекер/git. Для проду — окремо у Vercel env.

### Відновлення після збою: діагностуй, не ретрай
21. **Збій → root cause, не сліпий повтор.** *500 на прев'ю → перевір лог (Turbopack cache); порожній picker → перевір env (`grep -c KEY`).* Не жени ту саму команду в надії.
22. **Май плейбук відомих збоїв.** Turbopack SST-паніка → kill node + `rm .next` + один dev. Стале `.next/types` після видалення роуту → `rm .next`.

### Ефективність і темп
23. **Паралель незалежне, послідовно залежне.** Кілька Read/grep — одним махом; залежні — по черзі.
24. **Не пере-виводь встановлене.** Факт уже з'ясований у сесії — не грепай удруге.
25. **Гейти по тіру, не по звичці.** `tsc` щоразу; повний build батчем перед деплоєм, не після кожних 3 класів.

### Стан і передача
26. **Кожна одиниця роботи лишає слід.** commit → TRACKER/HANDOFF/TRANSITION → mempalace → SYSTEM_MAP. Наступна сесія стартує теплою.
27. **Пиши для себе-майбутнього.** У HANDOFF/drawer фіксуй не лише ЩО, а й УРОК + ЯК застосувати — щоб рішення переюзалось, а не перевідкривалось.

## V. Мета-урок співпраці

Що зробило роботу швидкою і якісною за Sprint-05 (83/86 ✅) + повний C-DESK-01 (8 стор десктопу) + M-SHOP-05:

1. **Founder дає закон один раз — agent кодифікує назавжди.** «Правило темного блоку», «прибирай емодзі» → у DESIGN_LANGUAGE + пам'ять → застосовується автоматично, без повторів.
2. **Чесність > згода.** Anti-sycophancy: коли ТТН-фаза мала зовнішній блокер (sender-профіль майстра) — сказав прямо й звузив до MVP, а не збудував 500 рядків на припущеннях. Коли знайшов латентний squeeze bookings — підсвітив, не сховав.
3. **Власні очі + рідкі дані** зняли головну фрустрацію (сліпі цикли, невидимий на реальних даних редизайн).
4. **Розумні дефолти + делегування.** «Все закінчуй, QA обирай найкращі» → agent веде автономно, але зупиняється на рішеннях, які **реально** змінюють що будувати (обсяг revenue-critical, зовнішній блокер).
5. **Пам'ять як важіль.** MemPalace + SYSTEM_MAP + HANDOFF = кожна нова сесія стартує з повним контекстом, не з нуля.
