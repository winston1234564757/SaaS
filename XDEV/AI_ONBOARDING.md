## 2. Загальні Директиви розробки BookIT

### 💎 ЗАЛІЗНЕ ПРАВИЛО: Глибокий Аналіз Логіки
**Аналізуй повну логіку функціоналу.** Дивись, де, що і як має працювати в комплексі (від БД до UI). Не роби поверхневих фіксів. Якщо бракує розуміння або контексту — **обов'язково запитуй уточнення** у користувача перед початком робіт.

### 🔴 QA-GATE: Обов'язкова сесія перед будь-якою зміною
Ніколи не починай реалізацію нового функціоналу або рефакторинг існуючого (включно з виправленням логічних багів) без QA-сесії.
QA-сесія — це пропонування варіантів вирішення та узгодження з користувачем відповідей на питання:
```
1. ЩО саме змінюємо? (файл, таблиця, RPC)
2. ЧОМУ? (причина багу або бізнес-вимога)
3. ЯКЕ рішення пропонуємо? (підхід у 2-4 реченнях, не код)
4. ЩО може зламатись? (суміжні компоненти, RLS, типи)
5. ЯК перевіримо? (SQL, manual, E2E)
```
*Виключення:* виправлення очевидної typo (один символ), додавання/видалення `console.log` для дебагу, grep-пошук.

### DB-to-DOM Thinking
Проектуй фічі знизу вгору:  
**DB Schema ➔ Server Action ➔ Form Input ➔ UI Component**  
Ніколи не починай з UI без розуміння як стан персистується. Перед рендером перевіряй три шари (DB Layer, Input Layer, Mutation Layer) згідно з [AI_DEVELOPER.md](file:///C:/Users/Vitossik/SaaS/XDEV/AI_DEVELOPER.md).

## 3. Що Заборонено Категорично
*Повний опис критичних антипатернів дивись у Конституції розробника [AI_DEVELOPER.md](file:///C:/Users/Vitossik/SaaS/XDEV/AI_DEVELOPER.md#-критичні-антипатерни-написано-кровю-релізів).*
- `any` у TypeScript заборонено абсолютно.
- `window.location.reload()` ➔ тільки TanStack Query invalidation.
- `getSession()` в queryFn ➔ призводить до deadlock.
- `AnimatePresence mode="wait"` для елементів змінної висоти ➔ тільки `mode="popLayout"`.
- `onAuthStateChange` deps ➔ тільки `[supabase, fetchProfile]`.
- Емодзі у коді інтерфейсу ➔ заборонено. Тільки іконки Lucide React.
- Згадки або інтеграції `WayForPay` ➔ заборонено. Тільки Monobank.

## 4. Протокол Верифікації Змін

Після кожної реалізації або фіксу AI-агент зобов'язаний надати відповідний протокол верифікації.

### 4.1 Ручний Тест (для користувача)
Виконується в браузері. Надай покроковий чеклист у такому форматі:
```markdown
## Ручний Тест: [Назва фічі/фікса]

**Передумови:**
- [ ] Опис передумов (наприклад: "Увійти як майстер")

**Кроки верифікації:**
- **Крок 1:** Перейти на [URL], натиснути [Кнопку].
- **Очікуємо:** [Опис очікуваного преміального результату].
- [ ] Успішно

**Мобільна перевірка:**
- [ ] Перевірити BottomSheet (`vaul`) на мобільній версії (ширина 375px).
```

### 4.2 SQL Тест (для перевірки DB-змін)
Надай SQL-скрипти верифікації у такому форматі:
```sql
-- SQL Верифікація структури та RLS
SELECT column_name, data_type FROM information_schema.columns WHERE table_name = 'назва_таблиці';
SELECT tablename, rowsecurity FROM pg_tables WHERE tablename = 'назва_таблиці';
-- Перевірка індексів та Foreign Keys
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'назва_таблиці';
```

### 4.3 E2E Тест (Playwright)
Проект використовує Playwright. Тести знаходяться в `e2e/tests/`.
- Звертатися до елементів дозволено виключно через `data-testid` (не через класи чи текст).
- Після тестів обов'язковий `test.afterEach` cleanup для збереження чистоти БД.
