# REPO-PARITY — стан і безпечна процедура (2026-07-08)

> Контекст: більшість P0/P1-фіксів R2 застосовано на прод через **Supabase Management API**
> (`/database/query`), а НЕ через `supabase db push`. Тому prod-стан ≠ repo-стан у двох вимірах:
> (1) **тіла функцій** (guardи жили лише на проді), (2) **реєстр міграцій** (`schema_migrations`).
> Деплой-флоу зараз: `vercel --prod` (код) + Management API (DDL). `db push` НЕ використовується —
> desync латентний, нічого активно не ламає, але це пастка для того, хто наступним запустить push.

---

## ✅ HALF #1 — тіла функцій back-portовано (ЗРОБЛЕНО)

Міграція `supabase/migrations/20260708000000_repo_parity_idor_bodies.sql`:
- 23 функції витягнуто з проду через `pg_get_functiondef()` (авторитетні guarded-тіла).
- 21 IDOR-функція з `auth.uid()`-guard (owner p_master_id / p_referrer_id для `get_c2c_balance`),
  `get_freed_slot_clients` — 2 оверлоади (обидва guarded).
- `claim_phone_discount` — свідомо БЕЗ owner-guard (викликає клієнт, не майстер; захист = REVOKE anon).
- `decrement_product_stock_atomic` — існував на проді, у репо був ВІДСУТНІЙ повністю; тепер у репо.
- REVOKE/GRANT re-assert у кінці (order-independent за fresh push; дзеркалить `20260706120000`).
- Ідемпотентна (CREATE OR REPLACE = no-op проти прода), безпечна для повторного застосування.

**Результат:** репо-джерело функцій = прод. Майбутній `db push` (після Half #2) відтворить guardи,
а не зрегресує до легасі-тіл.

### Чому НЕ можна робити repair наосліп
`supabase migration repair --status applied <v>` пише в реєстр. Якщо позначити «applied» те, що
реально НЕ застосовано на проді → `db push` пропустить → **прод назавжди без цієї зміни** (тихий злам).
Asymmetric risk: помилка незворотна. Тому кожну з 47 треба звірити з фактичним прод-станом ПЕРЕД repair.

### Безпечна процедура (виконати ПЕРЕД будь-яким `db push`)
1. `supabase migration list` — CLI покаже local-vs-remote діф (він рахує це сам, надійніше за ручний grep).
2. Для КОЖНОЇ з 47 незареєстрованих: підтвердити наживо через Management API, що зміна вже на проді
   (колонка/функція/таблиця існує). Приклади:
   - `138-145` (products fix, service icon) — перевірити колонки `products`/`services`.
   - `20260706120000/20260707130000/131000/132000/20260706000000/20260708000000` — застосовані API
     (billing cols, sms_table, enum in_app, NP fields, IDOR bodies) → підтверджено раніше = **applied**.
3. `supabase migration repair --status applied <v>` для тих, що ПІДТВЕРДЖЕНО на проді.
4. Ті, що реально ще НЕ на проді (якщо знайдуться) — лишити для `db push` застосувати.
5. **35 orphan-рядків**: вирішити окремо. Це прод-зміни без repo-джерела → або витягнути їх DDL з проду
   в repo-міграції (як Half #1), або (якщо це дублі repo-змін під іншими таймстемпами) лишити як є —
   вони не заважають push (push дивиться лише repo-файли, яких нема в реєстрі).
6. Після repair: `supabase migration list` має показати чистий збіг → тоді `db push` безпечний.

### Пріоритет
НЕ launch-блокер (поточний деплой не через push). Робити як окрему обережну задачу, коли реально
знадобиться `db push`, або в межах post-launch hygiene. Half #1 (важливіша, security-relevant) — закрита.
