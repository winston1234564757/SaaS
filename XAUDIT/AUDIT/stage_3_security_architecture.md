# Звіт про аудит: Етап 3 (Безпека та архітектура авторизації)

Ми проаналізували механізми безпеки, захисту маршрутів, автентифікації та обробки платежів.

## 1. Захист маршрутів (Routing Guard / Middleware)
- **Файл**: `src/middleware.ts` (коментарі в коді посилаються на `proxy.ts`, але логіка повністю консолідована в офіційному middleware Next.js).
- **Механізм роботи**:
  - **Нульовий мережевий запит**: Для прискорення завантаження middleware спочатку перевіряє наявність сесійного кукі `-auth-token` локально. Якщо його немає, запити на приватні сторінки `/dashboard`, `/my` та `/onboarding` миттєво перенаправляються на `/login`.
  - **Кешування ролей**: Роль користувача зберігається в кукі `user_role` та `user_role_uid`. Якщо кукі відсутні, виконується разовий запит до Supabase DB (з таймаутом 3 секунди для захисту від «холодного старту») для визначення ролі (`master` або `client`), після чого роль записується в кукі.
  - **Перевірка прав**: Доступ до `/dashboard` дозволено лише для користувачів з роллю `master`. Користувачі з роллю `client` перенаправляються на `/my/bookings`.

## 2. Авторизація через SMS OTP (TurboSMS)
- **Файли**: `/api/auth/send-sms` та `/api/auth/verify-sms`.
- **Безпека від спаму**: Запобігання TOCTOU (Time-of-Check to Time-of-Use) перегонів за допомогою збереженої процедури `check_and_log_sms_send`, яка використовує блокування `pg_advisory_xact_lock` на рівні IP та номеру телефону.
- **Генерація OTP**: Використовує криптографічно стійкий генератор `crypto.getRandomValues(new Uint32Array(1))` для створення 6-значних кодів.
- **Порівняння кодів**: У `verify-sms` порівняння введеного OTP з кодом з бази даних виконується за допомогою `timingSafeEqual` з модуля `node:crypto`, що повністю нівелює ризик timing-атак.
- **Автоматична лінковка**: Після успішного підтвердження телефону гостьові бронювання з відповідним номером телефону автоматично зв'язуються з новоствореним користувачем (через `client_id`).

## 3. Безпека вебхуків Monobank
- **Файл**: `/api/billing/mono-webhook`.
- **Криптографічний підпис**: Monobank використовує ECDSA P-256 + SHA-256 (не Ed25519, що є важливою технічною детальною розбіжністю з первинною документацією, але відповідає офіційному API банку).
- **Валідація підпису**:
  - Публічний ключ кешується на 24 години і завантажується безпосередньо з `api.monobank.ua`.
  - Використовується `createVerify('SHA256')` з бібліотеки `node:crypto`. У разі збою підпису миттєво повертається `403 Forbidden` (без м'якого режиму).
- **Захист від Replay-атак**: Webhook перевіряє мітку часу у параметрі `reference` (формат `bookit_{tier}_{uid32}_{timestamp}`). Якщо вік запиту перевищує 15 хвилин, він відхиляється зі статусом `400 Bad Request`.
- **Ідемпотентність**: Запис про транзакцію вставляється в таблицю `billing_events` з унікальним обмеженням на `payment_id`. У разі дублювання транзакція ігнорується, повертаючи клієнту успіх (код `200`).

## 4. Безпека Vercel Cron-завдань
- **Адресація**: `/api/cron/*`.
- **Захист**: Кожен обробник перевіряє заголовок `Authorization`. Першим рядком виконується порівняння зі значенням `Bearer ${process.env.CRON_SECRET}`. У разі неспівпадіння миттєво повертається `401 Unauthorized`.
