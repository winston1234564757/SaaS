# 🔬 Поглиблений діагностичний звіт: BookIT (Deep Audit)

Цей звіт містить вичерпний перелік технічного боргу, архітектурних розбіжностей, проблем із типізацією та потенційних витоків пам'яті, виявлених під час детального аналізу кожної лінії коду платформи BookIT.

---

## 🚨 КРИТИЧНІ НЕВІДПОВІДНОСТІ (Launch Blockers & Bugs)

### 1. ⚙️ Ліміти підписок: Starter Plan
* **Статус**: 🟢 **ВИПРАВЛЕНО**
* **Проблема**: Розсинхрон між документацією (`50` записів/місяць) та кодом (`30` записів/місяць).
* **Виконані дії**: 
  - Оновлено ліміт у серверному екшені `createBooking.ts` (ліміт змінено з 30 на 50, виправлено повідомлення про помилку).
  - Синхронізовано хук `useBookings.ts` (встановлено ліміт 50).
  - Оновлено блок Starter-тарифу на лендингу `LandingPricing.tsx` (вказано "До 50 записів на місяць" та додано чітке "До 5 Flash-акцій/міс", оскільки ліміт флеш-акцій `STARTER_LIMIT = 5` раніше взагалі не фігурував на лендингу).

### 2. 🧠 Витоки пам'яті в життєвому циклі React 19 / Next.js 16
* **Статус**: 🟢 **ВИПРАВЛЕНО**
* **Витоки в `TelegramProvider.tsx`**:
  - *Симптом*: У `useEffect` ініціалізації запускався `safetyTimer` на 8 секунд та повторювані таймери `initWithRetry`. При швидкому розмонтуванні компонента таймери продовжували виконуватись у фоні, викликаючи `setIsReady(true)` на неіснуючому DOM-вузлі.
  - *Фікс*: Додано `cancelled` прапорець та повне очищення таймерів через `clearTimeout` у callback розмонтування `useEffect`.
* **Витоки в `LocationPicker.tsx`**:
  - *Симптом*: Google Maps API вимагає очищення нативних слухачів подій (`click`, `dragend`, `place_changed`). Вони залишалися активними після видалення карти.
  - *Фікс*: Додано очищення через `google.maps.event.clearInstanceListeners` для карти, маркера та автокомпліту.

## 🟡 ТЕХНІЧНИЙ БОРГ ТА АРХІТЕКТУРНІ ЗАУВАЖЕННЯ

### 1. ❌ Масове порушення Конституції: Тип `any` у TypeScript
* **Статус**: **ПОТРЕБУЄ РЕФАКТОРИНГУ**
* **Проблема**: Згідно з Конституцією: *"Strict mode — any ЗАБОРОНЕНО абсолютно. Немає виключень"*. Проте пошук виявив **120+ випадків використання `: any` або `as any`**.
* **Критичні файли з `any`**:
  - `src/lib/supabase/hooks/useOrders.ts` (рядки 86, 100, 125, 126, 127) — нетипізоване мапування замовлень та продуктів.
  - `src/components/master/pricing/DynamicPricingPage.tsx` (рядки 112, 182, 185, 205, тощо) — обробники подій та параметри налаштування правил ціноутворення використовують `any` замість конкретних типів інтерфейсу `PricingRules`.
  - `src/components/master/settings/hooks/useSettingsForm.ts` (рядки 143, 286) — нетипізована обробка відповідей API.
  - `src/components/shared/BentoBottomNav.tsx` (рядки 168, 195) — властивості `NavItem` та `BentoTile` передаються без інтерфейсу.
  - `src/types/database.ts` (рядок 122) — поле `segment_config?: any[] | null`.
* **Рекомендація**: Створити окрему задачу на повну ліквідацію `any` у `src/` та заміну їх на суворі типи з `database.ts` або Generics.

### 2. 🎁 Маркетинговий обман: "Кешбек" (Loyalty Program)
* **Статус**: **UX/COPYWRITING БОРГ**
* **Проблема**: На лендингу `LandingBentoFeatures.tsx` зазначено: *"Кешбек — змушує повертатись. Ваші бали: 380 = 76 ₴"*. Проте реальна таблиця `loyalty_programs` та сторінка авторизації клієнта використовують звичайну логіку накопичувальної знижки на візит (наприклад, *"5-й візит = знижка 20%"*). Немає жодного балансу балів чи конвертації у гроші.
* **Рекомендація**: Змінити тексти на лендингу та в кабінеті клієнта з "Кешбек/Бали" на "Автоматична знижка за лояльність на N-й візит", щоб уникнути скарг користувачів на відсутність балансу балів.

### 3. 🏗️ Напівфабрикат: Модуль "Студія" (Studio Dashboard)
* **Статус**: **ЧАСТКОВО ГОТОВО (Заглушка)**
* **Проблема**: У базі даних є всі необхідні таблиці (`studios`, `studio_members`), працює флоу приєднання до студії клієнтів. Однак сама сторінка дашборду `/dashboard/studio` є простою заглушкою з формою списку очікування (`WaitlistButton`). Власник салону не має реальних інструментів для перегляду та управління майстрами.
* **Рекомендація**: Заблокувати можливість оплати тарифу Studio у білінгу до повної реалізації кабінету управління салоном.

### 4. ⏳ waitlists: Черга очікування для клієнтів
* **Статус**: **АРХІТЕКТУРНИЙ ПРОПУСК**
* **Проблема**: Таблиця `waitlists` у Supabase існує, але використовується тільки для майстрів, які записуються на ранній доступ до фіч. Справжнього клієнтського функціоналу waitlist (стати в чергу на зайнятий слот майстра і отримати пуш при скасуванні) немає ні в UI `BookingWizard.tsx`, ні на бекенді.
* **Рекомендація**: Або реалізувати повноцінний клієнтський Waitlist, або перейменувати таблицю `waitlists` -> `feature_waitlists`, щоб уникнути плутанини в майбутній архітектурі.
